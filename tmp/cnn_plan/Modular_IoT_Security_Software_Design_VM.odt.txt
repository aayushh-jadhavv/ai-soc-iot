Modular IoT security gateway software design
Gateway CNN IDS and Android application
This design specifies a reusable IoT security gateway, a compact convolutional neural network intrusion detector, and an Android application with local Llama explanations. The gateway observes routed traffic, records evidence, selects a response, and maintains an audit trail. The CNN supplies fresh scores for successive observations. The app synchronises reports and lets an authenticated administrator inspect devices, acknowledge incidents, and request restriction or release.
The current implementation target is a native-architecture Linux virtual machine on the available computer, with CPU inference and a virtual routed IoT network. No Raspberry Pi or other development board is available or required. This reproduces the gateway software workflow, not Raspberry Pi 5 hardware. Android phones remain a separate app test environment. Arm64 emulation is an optional future compatibility experiment, not a completion requirement.
Version 1.1 design dated 13 November 2026. This revision replaces board prerequisites with native Linux VM validation and adds Python-based experiment measurement. Numerical settings remain proposed starting values unless identified as paper settings. Freeze them in experiment configurations and adjust only using development data. No detection or performance results are claimed here.
For a team or mentor discussion, begin with Sections 1 to 3 and the worked example. For implementation, agree on Sections 4 and 5 first, then assign Sections 6, 7 and 8 to the three module owners. Sections 9 to 11 provide the laboratory workflow and completion checklist. The final sections explain limitations, terminology and sources.
1 Decisions and corrections to the proposed idea
The three-part architecture is appropriate. Its central policy engine needs explicit responsibilities, reproducible inputs, and durable state. The following corrections make the implementation coherent.
Topic
Specification to implement
Network installation
In the current lab, place virtual clients downstream of the gw namespace, using isolated bridges and explicit routes. A host or VM joining an existing LAN does not automatically observe its traffic.
Continuous inference
Score each new valid eight-second sequence. Retain recent results as evidence. A cached old result cannot classify changed traffic.
Central decision making
The gateway owns policy, device state, actions, recovery, and reports. The CNN owns input validation, preprocessing, inference, and model metadata.
Scores and evidence
Store the CNN score and repeated-observation count separately. A sigmoid score is uncalibrated until calibration is evaluated. Repetition does not automatically increase model confidence.
Response scope
A device score concerns traffic associated with that device. Restrict a source only when independent direction and identity evidence supports that target. Record unknown roles explicitly.
Recovery
Use expiry and bounded probation with approved communication. Silence caused by filtering does not demonstrate remediation.
Dataset use
Train, validate, and internally test on UNSW-NB15. Use CICIDS-2018 and BoT-IoT as separately reported external tests after applying the same raw-PCAP extractor and label rules.
Compression
Use GA-guided channel selection, physically rebuild the smaller network, fine-tune it, and measure the exported model. Zero-filled tensors alone do not provide dense runtime savings.
Persistent reports
Write reports and action outcomes to SQLite on disk. Keep short feature histories in RAM.
Explanations
Store a factual reason when making the decision. The phone produces a later Llama explanation linked to that report revision.

The release has two execution modes using the same contracts. OBSERVE is the default and records recommendations with NOT_EXECUTED status. ENFORCE is enabled explicitly for a configured laboratory or deployment and applies validated rules. Implementing and testing ENFORCE is a separate integration milestone. The app displays the actual execution status in both modes.
The research contribution to evaluate is the trade-off between detection quality and the cost of a GA-pruned temporal CNN, integrated with reproducible gateway observations and factual local reporting. The studies motivate different parts of the design. LiReS supplies the pruning approach, IoT-KEEPER motivates gateway monitoring and policy organisation, and IoT SENTINEL informs controlled network enforcement. This design does not establish the enclave protection evaluated by LiReS. [S1, S2, S17]
1.1 A simple worked example
Consider a camera that normally communicates with its approved server. In an illustrative laboratory incident, it begins contacting many other destinations.
1. The gateway sees the packets, identifies the camera's current network attachment, and measures counts, sizes, destinations and timing every second.
2. After eight valid seconds, the CNN receives those eight rows. It then scores a newly updated sequence every second. Suppose several scores are high.
3. The policy engine checks the recent scores and independent observations. It sees that the camera initiated the unusual connections. It records the evidence and recommends a limited communication profile.
4. In OBSERVE mode the report says that restriction was suggested. In ENFORCE mode the helper installs and verifies the rule before the report says that restriction was installed. An installation failure is reported as a failure.
5. The app downloads that report. Its factual summary appears immediately. Llama can explain that repeated high scores and unusual outgoing connections led to the recommendation, while preserving whether it was executed.
6. An administrator can acknowledge the incident, inspect the camera's history, or request release. A timed review uses controlled probation; a quiet blocked camera is not automatically declared healthy.
This example illustrates the workflow. It is not a measured detection result, and a high score alone would not justify blaming or blocking the camera.

Use three independently testable deliverables in one repository. The CNN library runs inside a dedicated local inference worker process on the gateway. 3 Network placement and installation
3.1 Reference routed virtual deployment
Use the following path inside the native Linux VM. Section 9.1 defines the namespace topology; no physical board, access point or USB network adapter is required.
Virtual IoT clients -- isolated IoT bridge -- IoT interface of gw
gw namespace routing and capture in the Linux VM
Service namespace -- isolated service bridge -- upstream interface of gw
Android administrator --------- Allowed management path

Create two veth-backed gateway interfaces connecting separate IoT and service bridges. Configure clients to use gw as their IPv4 default router and configure the service return route. Start with static addresses; test DHCP through dnsmasq within the isolated lab if discovery is in scope. Do not run lab DHCP on the host ordinary LAN. A later physical deployment would need its own interface and attachment validation. [S12]
Example deployment configuration uses IoT subnet 10.77.10.0/24 and gateway 10.77.10.1, with an upstream network chosen to avoid overlap. DHCP runs only on the intended IoT segment. If the upstream router has no return route for 10.77.10.0/24, IPv4 masquerading is an implementation option. Capture on the IoT side before address translation to retain device attribution.
Keep the virtual traffic path explicit. Attach clients and services to different isolated Linux bridges, with no default container or host route bypassing gw. Connecting a VM to the normal LAN alone does not route other devices through it. A future physical Wi-Fi deployment would require a separate attachment and coverage review.
The first lab explicitly supports IPv4. Disable IPv6 forwarding and router advertisements on its isolated test segments and verify there is no alternative IPv6 route. A production dual-stack profile must implement equivalent IPv6 capture, registry bindings and filtering before declaring dual-stack coverage. The restricted lab profile must not silently leave IPv6 as an unmonitored bypass.
3.2 Coverage and later deployment options
Same-subnet device traffic may remain inside the AP or switch. Label this coverage boundary in the app's gateway-health screen and the submission. A transparent bridge adapter can preserve endpoint addressing when inserted between a separate AP/switch and the router, but the downstream peer-traffic boundary still applies.
IoT SENTINEL used OVS with a custom controller and configured wireless isolation plus OpenWrt/Linux forwarding to route wireless peer traffic through its enforcement point. Its strict level still allowed communication inside an untrusted group. Adopt controlled attachment points and explicit per-device allowances if extending this project. Full peer isolation needs compatible AP/switch configuration or segmentation. [S2]
3.3 Installer sequence
1. Read selected IoT and upstream interfaces, subnets, existing routes and DHCP ownership. Stop on overlap or an ambiguous interface selection.
2. Create the gateway identity, database directory and restricted operating-system users. Save the initial network configuration for recovery.
3. Configure routing and exactly one DHCP authority for the IoT segment. Install an explicit baseline firewall with a preserved administrator path.
4. Set the administrator password at the local console. Generate the gateway TLS identity and a pairing QR containing its public certificate and endpoint, excluding the password.
5. Install the verified model bundle and services. Start in OBSERVE mode and expose health information.
6. Renew one test client's DHCP lease. Verify its default route, a bidirectional capture and loss of upstream reachability when gateway forwarding is disabled in the lab.
7. Pair the app, fetch a real report and test the documented local recovery procedure before enabling enforcement.

Count physical packet observations, including retransmissions. Do not deduplicate legitimate TCP retransmissions. Prevent double capture at the input source by selecting one observation interface. For offline captures, verify whether multiple sensors have created duplicates before processing. IP and port uniqueness sets are scoped to one device and one window.
For zero outgoing packets, all outgoing statistics are zero. A single outgoing packet has zero length standard deviation and zero inter-arrival statistics. One inter-arrival gap has zero standard deviation. Inter-arrival times use only pairs inside the current window. Count IP bytes rather than link-layer bytes, and never substitute a dataset's flow-byte field without verifying the definition.
The v1 parser accepts complete, non-fragmented IPv4 packets with accessible required headers. Account for fragments, truncation, malformed headers, unsupported link types and unsupported protocols in quality counters. Mark a window affected by unsupported packets or capture drops as degraded and abstain from automatic escalation. Keep unsupported traffic visible as a coverage event. Add a separately versioned extractor if later supporting reassembly or IPv6.
4.1 Window and history rules
Use half-open time intervals [start, end), aligned to integer seconds of event time. In the live adapter, maintain a mapping between packet timestamps and the monotonic clock. Finalise each window after a proposed 100 ms ordering allowance. Reject late arrivals from already finalised windows and emit a quality event. For offline extraction, sort packets by their recorded timestamp within each original capture and use the same window boundaries.
A healthy capture with no packets yields a valid zero row. An input gap, worker restart, timestamp discontinuity or known capture drop yields invalid coverage. Reset the eight-row history after such a gap and require eight fresh valid rows. Include zero rows during monitored idle periods, but stop inference after a configurable inactivity timeout, initially 60 seconds. On reactivation start a fresh history. Define offline extraction with the same lifecycle.
Keep short raw observations for evidence separately from the feature vector, including up to 32 recent connection summaries and direction/initiator indicators. The numerical model input excludes device identifiers, IP addresses, capture filenames, dataset names and labels.
The current features emphasise volume, spread and timing. They can miss attacks whose metadata resembles normal use. Incoming flood behaviour may justify additional incoming protocol and timing features later. Test a proposed v2 schema through an ablation experiment and retrain every affected model. Do not silently change the v1 vector.

Require 16 finite non-negative numbers in schema order. Count and byte fields must be integral before conversion to float32. Reject NaN, infinity, negative counts and intervals other than 1000 ms. IDs are bounded strings. Times are signed 64-bit epoch milliseconds and sequence numbers are monotonically increasing integers within a capture session. device_id is a gateway UUID in deployment; compact IDs above improve readability.
Binding revision identifies the address/attachment mapping used for this observation. Enforcement revision identifies the policy affecting the observed traffic. These fields let the gateway reject a result generated for an old address binding or a different restriction state.
5.2 FeatureSequence and inference service
POST /v1/predict on the local IDS worker accepts request_id, model_id and windows. windows is an array of exactly eight complete FeatureWindow objects, oldest first, with the same device, binding, session, feature schema and enforcement revision. Require contiguous timestamps and sequence numbers. The request carries raw measurements. The IDS performs training-fitted preprocessing exactly once.
Internally, build a matrix with shape [8,16], apply preprocessing feature-wise, transpose to [16,8], and add a batch dimension to obtain float32 [1,16,8]. The model bundle declares that layout. Reject a request for a different model version with MODEL_MISMATCH rather than silently selecting another model.
GET /v1/metadata returns model_id, task, feature_schema, input_shape, preprocess_hash, model_hash, runtime version and calibration status. GET /v1/health reports model loading, ready state and recent errors. These local endpoints require the service credential and bind to loopback only.

The result identifies the scored sequence through request_id and last_window_id. Its score concerns attack-associated traffic in the final second, using earlier seconds as context. It does not establish whether the device is the attacker or victim. status is ok, abstain or error; attack_score is null unless status is ok. An inference score has range [0,1]. Only add an attack category if a separately validated multiclass model produces it.
Set a proposed request deadline of one second. Retry an identical request once with its original ID. A result cache may reuse only an exact request and model version. Keep a bounded cache of 256 requests for 60 seconds and reject reuse of a request ID with different content. New windows always create new requests.
The gateway accepts a result for policy escalation only when it matches the current device binding, enforcement revision and expected request. Discard results whose final window is more than five seconds old for automated response, while recording their delay. Errors and abstentions create health information and do not become benign classifications.
5.4 PolicyDecision and ActionResult
PolicyDecision contains decision_id, incident_id, device_id, binding_revision, policy_version, evidence_window_ids, inference_request_ids, observed_state, recommended_state, action_scope, reason_codes, created_at_ms and review_after_ms. action_scope specifies device or connection, direction, address family, approved endpoints and services, plus duration. A connection uses protocol, source and destination addresses, and source and destination ports.
ActionResult contains action_id, decision_id, mode, status, rule_revision, installed_rule_ids, attempted_at_ms, confirmed_at_ms and error. Allowed status values are PENDING, NOT_EXECUTED, INSTALLED, FAILED, EXPIRED and REPLACED. Dry-run returns NOT_EXECUTED. Success means the helper has read back the expected installed rule revision. A separate connectivity test establishes that the intended path is actually affected.
An administrator request uses a client-generated UUID as an idempotency key and the expected current device-state revision. Duplicate requests return the original result. A stale revision returns HTTP 409 so the app refreshes before trying again.
5.5 IncidentReport and event synchronisation
IncidentReport contains report_id, revision, gateway_id, incident_id, device identity snapshot, affected time range, raw feature windows, inference results, observations, policy decision, action result, factual_summary, coverage, model/schema/policy versions and created_at_ms. Preserve the event-time addresses, even when the registry changes later.
Every new report revision creates an immutable event with a gateway-local increasing event_seq. A closure, acknowledgement, failed action or password change is a new event. Do not delete an old alert when it clears. An app keys cached reports by gateway_id, report_id and revision and synchronises by event_seq, so concurrent phones cannot cause one another to miss reports.
Reports can contain sensitive addresses. Send only the evidence needed for explanation, cap the number of stored connection examples, and render captured text as plain text. Preserve numbers, units, confidence limitations and execution status in the factual summary.
6 Implementing the gateway
6.1 Capture and device registry
Start with a PCAP input adapter and a live libpcap adapter that produce the same PacketRecord. PacketRecord contains event time, observation interface, link type, source/destination MAC if visible, source/destination IP, protocol, accessible ports, IP length, TCP flags and parse-quality status. ARP and DHCP information update registry observations separately. Ordinary ARP is outside the model's IP feature counts and does not itself invalidate a window.
Use a static registry file for the first virtual experiment. Add DHCP lease events and neighbour-table observations to discover devices automatically. Persist a generated device_id with first_seen, last_seen, friendly_name, attachment interface, address bindings, binding validity intervals, identity source and binding revision. Maintain last-seen history rather than overwriting an old IP-to-device relationship.
A DHCP lease is an address-assignment observation, not cryptographic identity. If two attachments claim one address or an address is reassigned, increment the binding revision, clear the relevant feature history, and suspend automatic restriction until the mapping is resolved. A MAC change creates a new provisional identity unless the administrator confirms a merge. Preserve both records and their audit history when merging.
For each packet, update the source device's outgoing counters and destination device's incoming counters when each is a monitored local endpoint. Never use the upstream router's MAC to identify a remote host. Multicast and broadcast packets count for an observed sender, but do not manufacture a received packet for every possible recipient. The gateway reports only packets visible at its observation point.
Keep the capture process minimally privileged. Send parsed records through a bounded queue. On queue overflow, record counts, affected time and degraded coverage, then reset affected histories. If the lost packets cannot be attributed, invalidate all active device histories for that interval. A stale backlog must not produce current restrictions. Keep per-device counters, online means and variances, and capped uniqueness sets. A suggested initial limit is 128 tracked devices and 4096 distinct destinations or ports per device/window. If a set overflows, flag that window and preserve a lower-bound diagnostic instead of treating a clipped value as exact.

Proposed defaults are t_alert = 0.70, t_high = 0.90 and t_clear = 0.40. Replace these with values selected on UNSW validation data. Raise a visible incident after two of the latest three valid scores reach t_alert. A single crossing stays WATCH and can be logged without a notification. Recommend restriction after three of the latest five scores reach t_high, plus corroborating observations, reliable device binding, a usable service profile and fresh capture. These overlapping sequences are correlated evidence. Report their count without multiplying probability or inventing certainty.
Corroboration is deterministic, with recorded thresholds. For a scanning scenario, a proposed lab rule is at least 20 unique destinations or destination ports in five seconds, combined with device-originated connection attempts. Validate it against normal discovery behaviour before use. This rule is a policy heuristic independent of the CNN, and the report must identify its origin. One binary model score does not name an attack family or isolate a particular connection.
For a flood scenario, add a separate corroboration rule based on sustained packet or byte rate, initiator direction and a configured service-specific limit. Derive that limit from benign development workloads, including bursts, and freeze it before testing. If a service has no validated profile, issue an alert instead of an automatic restriction. A universal rate limit would risk blocking legitimate video or firmware transfers.
Role evidence uses observed connection initiation, TCP handshakes when available, direction, target spread and configured topology. If the evidence points to an external sender attacking a local receiver, recommend a narrowly scoped incoming-source rule when justified. Do not quarantine the receiver solely because its traffic scored high. If source attribution is uncertain, retain an alert and request review. Spoofable source addresses limit attribution strength.
Degraded capture, stale inference, unknown identity, schema mismatch and service failure suspend new automatic escalations. An alert clearance appends an event saying that recent evidence fell below the configured criteria. It does not erase the original report or establish that malware was removed.
6.4 Recovery without treating silence as success
On restriction installation, reset the normal-state feature history and record the new enforcement revision. Capture ingress traffic before the forwarded packet is dropped where the Linux capture path permits it, and also read firewall drop counters. A persistent forbidden attempt is useful evidence even when the packet never reaches its destination. Absence of attempts remains ambiguous.
Use a proposed 300-second review deadline and 120-second probation interval. These are policy settings, not unconditional automatic release timers. At the deadline, keep the restriction if the device has no approved recovery profile. A probation profile can permit its broker, configured DNS and an isolated test service, with explicit rates where implemented. Keep blocked destinations blocked during that trial.
After a policy change, gather eight fresh valid seconds before using model scores from that regime. Log enforcement context because filtered traffic has a different distribution from the training set. Recovery additionally requires healthy capture, meaningful observed approved activity, no new forbidden attempts, and either administrator confirmation or a validated automatic policy. A silent or disconnected device stays unresolved. A clean limited trial only establishes behaviour under that trial's permissions.
Limit automatic probation attempts to two per incident initially. Recurrence restores the restriction and records why. Manual release is an audited command with a reason and a temporary monitoring period. Emergency management access and the helper's local recovery control must remain reachable through explicit rules.
6.5 Enforcement adapter and crash consistency
Implement DryRunEnforcer first. Given a validated action, return its scope and NOT_EXECUTED status without changing networking. Then implement NftablesEnforcer for the controlled routed lab. Accept only typed addresses, protocols, ports, durations and predefined action enums. Reject arbitrary shell fragments or firewall text from the app, Llama or model.
Use a dedicated nftables table and owned rule identifiers. Keep baseline routing and administrator access separately managed. Apply device-specific deny/restrict logic before general established-connection acceptance so an existing session cannot bypass a new restriction. When required, remove only the relevant connection-tracking entries after validating the exact scope. Test behaviour for both existing and new connections.
nftables can apply a batch atomically, reducing partial rule changes. This does not make a database write and a kernel rule update one transaction. [S14]
1. In one SQLite transaction, write the decision, factual explanation, PENDING action and a durable work item.
2. The privileged helper consumes the work item with its action_id and expected device-binding revision.
3. Validate that the device still owns the attachment/address and that the action preserves the configured management exceptions.
4. Apply an idempotent rule batch. Read back the owned rules and return their revision and identifiers.
5. Commit the ActionResult and a new report revision. Mark the work item complete only after this commit.
6. On restart, compare pending actions and desired rules with the helper's actual rules. Reapply or reconcile by action_id without duplicating rules.
The helper should use CAP_NET_ADMIN in the test namespace or a tightly restricted service. The API and CNN processes run without it. Existing rules remain if the analysis worker crashes. Record a monitoring failure. The initial design uses expiring review schedules managed durably rather than unconditionally removing protection when the application restarts. Define and test the installer removal/recovery path for stale rules.
6.6 Persistence and report retention
Create tables for devices, bindings, incidents, inference_evidence, decisions, actions, events, admin_commands, sessions and configuration_versions. Add uniqueness constraints to window/request/action IDs and event_seq. Use an INTEGER PRIMARY KEY AUTOINCREMENT sequence for the append-only event feed and include a database epoch that changes after a restore or factory reset.
The default proposal retains incident reports for 30 days up to a 250 MiB cap, whichever is reached first. Persist full eight-window evidence for incidents and short health summaries for ordinary operation. Avoid writing every device's raw packet stream to flash. Cap report payloads at 64 KiB and paginated API responses at 1 MiB. Preserve open incidents preferentially and report retention loss explicitly.
When a phone presents a cursor older than retained events, return HTTP 410 with the earliest available cursor and a snapshot endpoint. Store the app cursor only after its local transaction commits. A database-full or unwritable-storage condition raises health status and suspends new automatic restrictions whose audit record cannot be persisted. Existing restrictions are reconciled rather than silently removed.

CICIDS-2018 DoS/DDoS cases can test a related family; FTP/SSH brute-force cases are an additional transfer experiment beyond those training families. Do not report a scan detector's failure on unrelated attacks as a same-task comparison without explaining the scope.
For a broader binary detector trained on all supported UNSW categories, retain the category metadata for per-family evaluation. The compact metadata schema may not distinguish every exploit or payload-based attack. Positive results on one selected subset do not establish coverage of the whole dataset or real IoT networks.
IoT-23 remains an optional alternative when per-connection labels and IoT captures are more practical to obtain. Changing to it would be a documented experiment choice. The implementation contract should not embed a dataset name, so that choice does not change the gateway or app.
7.2 Build the derived training data
1. Create a manifest containing dataset version, original capture ID, checksum, capture interval, link type, monitored-address map, ground-truth source and download provenance.
2. Inspect a small capture and labels first. Confirm time units/timezone, tuple orientation, IP mappings and capture completeness. Keep network identities outside model features.
3. Match labelled connections using source/destination IP, ports, protocol and time. Handle reversed packet direction within that connection. Report label match coverage and ambiguous matches. Do not label every device in an attack file as an attacker.
4. Assign the positive label to a device's final one-second window when packets associated with a verified malicious connection are actually observed for that monitored endpoint. This defines attack involvement, including potential victims. Silence outside packet observations must not inherit an entire long flow interval automatically.
5. Assign benign only to windows with reliable normal coverage. A mixture of verified benign and malicious packets is positive under this target definition. Treat contradictory annotations for the same traffic, uncertain identities and unsupported captures as unknown. Exclude unknown rows from supervised loss and count exclusions by reason. Flow labels are an approximation to packet behaviour and this limitation belongs in the experiment report.
6. Split original sessions or capture periods into training, validation and test groups before building sequences. Joined chunks from one capture stay together. Ensure each partition has usable benign and attack examples.
7. Run the shared extractor and create contiguous [8,16] samples per monitored device, with the final second's label. Reset at gaps and session boundaries. Save sample_id, group_id, device_id, last-window time, label, attack family, label quality and the numeric matrix.
8. Fit preprocessing on training windows. Store its values in the model bundle. Use the same preprocessing for every validation, internal test and external test sample.
Suggested partition proportions are 60/20/20 by independent session groups. UNSW's prepared CSV split cannot automatically provide a valid split for newly reconstructed temporal sequences. If only a few sessions exist, use documented non-overlapping chronological blocks and purge at least seven seconds of shared history plus any shared labelled connection across boundaries. Describe this as within-session evaluation. Never manufacture independent test sessions by randomly splitting overlapping samples.
Balance only the training sampler or loss. Keep evaluation prevalence as collected, and report benign/attack sample counts, device-hours and event counts. Limit each session's dominance in training so one high-rate attack cannot supply nearly every example. Fit preprocessing and any feature selection only on the training partition. [S13]
Cross-dataset evaluation is a generalisation test. Freeze weights, preprocessing, calibration and policy thresholds before it. Score CICIDS-2018 and BoT-IoT separately and show per-scenario results. If external data later guides tuning, record that it has become development data and reserve fresh captures for a new final test.

7.4 Genetic algorithm driven structured pruning
LiReS represents a candidate as a tuple of binary masks, one per prunable layer. One retains a filter and zero removes it. For masks m_l, the total units gamma = sum_l n_l, retained units Delta(c) = sum_l count_nonzero(m_l), and retention r(c) = Delta(c) / gamma. The paper maximises fit(c) = w(1-r(c)) + (1-w)acc(c), with w = 0.1 and accuracy expressed as a fraction. [S1, Section IV-B]
Its reported settings are population 100, at most 100 generations, crossover probability 0.6 and per-bit mutation probability 0.05. It uses roulette-wheel selection and a single crossover point in one selected layer mask. Its early stopping checks whether best-fitness improvement is below 1e-6. These settings describe the source and need not be affordable for the first run.
For this project, prune only the two hidden convolutional output-channel sets. Keep all 16 input features and the final binary output. Begin with population 20, maximum 15 generations, two retained elite candidates, crossover 0.6, mutation 0.05 and five-generation improvement patience. Include the all-ones baseline mask. Repair any candidate leaving fewer than four channels in a layer. Record these deviations from the paper.
Use a documented adapted search objective fit_project(c) = 0.1(1-r(c)) + 0.9 macroF1_validation(c). This handles class imbalance more explicitly than raw accuracy. Keep paper-mode fitness available for an ablation if resources permit. Reject deployment candidates whose final fine-tuned validation recall or macro-F1 falls more than 0.02 absolute below the selected baseline. This proposed acceptance tolerance must be registered before viewing final tests.
Implementation sequence is as follows.
1. Clone the trained baseline for each mask. Apply channel masks to layer outputs so removed units cannot contribute. Evaluate every candidate on the same fixed validation subset with gradients disabled.
2. Cache candidate evaluations by mask, baseline checkpoint hash and validation-manifest hash. Store fitness, per-class metrics and retained-channel indices.
3. Select parents, perform crossover, mutate and repair masks. Keep the elite candidates. Save best-so-far masks and fitness every generation.
4. Take the best feasible candidates and physically rebuild smaller layers. If I1 and I2 are kept channel indices, slice conv1 weights as W1[I1,:,:], conv2 as W2[I2][:,I1,:], and the output layer as Wout[:,I2]. Slice hidden biases accordingly and keep the output bias.
5. Before fine-tuning, compare compact-model outputs with the masked baseline on fixed inputs. This catches incorrect channel wiring.
6. Fine-tune the rebuilt model on training data, initially up to five epochs at learning rate 0.0001. Re-evaluate on validation data and apply acceptance tolerances.
7. Select and freeze one compact architecture. Report mask sparsity, parameter reduction, exported size, detection metrics and measured runtime. Counted channel sparsity and parameter reduction are different quantities.
Do not assume an 80 percent reduction or a speedup. If the direct small CNN gives a better measured result, preserve it as the deployment choice and report the GA comparison honestly. The GA experiment remains part of the research evaluation.
7.5 Export and runtime integration
Export a dummy baseline before full training to check the operator path. Use torch.export followed by ExecuTorch lowering to XNNPACK and save model.pte. Fix batch size one initially. If the chosen toolchain cannot lower Conv1D efficiently, use mathematically equivalent Conv2D kernels of size (1,3) with [1,16,1,8] internal input, and verify parity. Keep the external feature contract unchanged and record the internal layout in the manifest. [S6]
Deploy a bundle containing model.pte, manifest.json, feature_schema.json, preprocess.json, thresholds.json and reference inputs/outputs. The manifest includes model ID, task, checksums, trained categories, shape, runtime/export versions and provenance. Hashes detect accidental mismatch; use authenticated delivery or signatures when distributing bundles beyond the lab.
Load the bundle once in the inference worker. Validate schema and preprocessing hashes before readiness. Run warm-up inputs and numerical parity checks. An initial floating-point acceptance tolerance is absolute score difference at most 1e-4 on fixed reference inputs, with any threshold-crossing disagreement investigated. Quantised exports require a separately measured tolerance and full metric comparison.
Measure floating-point first. Optional INT8 quantisation uses representative training-only calibration data and must pass export and quality checks. Keep GA pruning and quantisation as separately measured steps. Model activation uses an atomic bundle-directory change, warm-up, health confirmation and a rollback copy. Keep two data streams separate. IDS training requires the raw PCAPs and reliable annotations in Section 7.1. Python instrumentation records model/training results; it does not generate trustworthy attack labels. Virtual MQTT/HTTP clients and Scapy fixtures can exercise the pipeline, but synthetic traffic is labeled as laboratory data and does not establish coverage of physical IoT devices.
Create a reusable Python measurement module used by training, GA search, export comparison and VM runtime tests. Use time.perf_counter_ns for elapsed times in one clock domain; measure preprocessing, forward inference, service round trip and report commit separately. Use torch.utils.benchmark for eager PyTorch CPU microbenchmarks and time the actual ExecuTorch runner through its Python binding or service boundary for deployed measurements. Use torch.profiler only in separate diagnostic runs because tracing adds overhead. [S18, S19]

Use pandas/PyArrow for tabular outputs and Matplotlib for plots; TensorBoard is optional and never the only record. The manifest includes code/data/model hashes, versions, seed, host/guest architecture, hypervisor, vCPU/RAM allocation, batch/thread settings and monitor configuration.
Benchmark in model.eval with gradients disabled. Start with 100 warm-ups and 1,000 timed calls, repeated three times, plus a 30-minute declared-load run. Report cold start separately from warm p50/p95 and throughput; retain raw observations. Compare models under the same VM and background-load settings. Do not infer physical-board power, energy, temperatures or Pi timing from software counters. If CUDA training is later available remotely, synchronise device work for timing and record allocated/reserved CUDA memory separately from CPU RSS.
8 Implementing the Android application integration
The existing dashboard supplies the interface. Retain it and implement a repository layer that replaces mock data with gateway API data. The app needs a local report store, synchronisation worker, administration client and Llama worker. Keep network and generation tasks off the UI thread.
8.1 Pairing and authentication
The administrator sets a password using the gateway's local installer. Store a salted Argon2id hash through a maintained library. OWASP's documented Argon2id baseline includes 19 MiB memory, two iterations and parallelism one; benchmark the chosen settings on the target runtime and rate-limit login requests. Never embed a shared password or session token in the APK or repository. [S10]
Pairing first establishes which gateway the phone should trust. The installer displays a QR containing gateway_id, the HTTPS endpoint and the gateway's public certificate or a fingerprint verified against a locally supplied certificate. The app stores that trust material in its app-private configuration. Certificate validation must authenticate the paired gateway before sending the password. A dynamic pin requires the matching certificate verification implementation, not a global trust-all TLS handler. Replacing the gateway key requires explicit re-pairing. Android supports custom trust configuration, but integration must be tested with the chosen client library. [S11]
POST /api/v1/auth/login accepts password and client_instance_id over authenticated TLS. It returns a random opaque session token, session_id, gateway_id, permissions, database_epoch and expires_at_ms. Store only a hash of the token on the gateway. Start with a 12-hour absolute session lifetime and require login again after expiry. Keep the password out of long-term phone storage.
Protect stored tokens with an Android Keystore-backed encryption key. Use a single administrator role for the first release. Because phones share one password, session IDs identify a client instance rather than a verified individual person. Record that distinction in the audit interface. Android Keystore provides protection for cryptographic keys; the application still controls how encrypted token data is used. [S15]
Changing the password requires the current password again, an authenticated session and a valid new password. In one gateway transaction update the password hash, increment auth_version and revoke all sessions. The phone then logs in again. Provide a local-console reset command for forgotten credentials, with session revocation and an audit event. Apply a per-client and global login rate limit, initially five failures per minute with increasing delay. Return uniform login errors.

8.3 Report synchronisation and storage
Poll the event endpoint every two seconds while the dashboard is open, with exponential backoff on failures. Fetch events after the app's committed cursor. In one Room transaction, upsert immutable reports/events and advance the cursor. Resume the same request after interruption. Retain a visible last-successful-sync time and cached-data indicator.
If the gateway's database epoch changes, request a snapshot. The snapshot is generated with a high-water sequence, after which the app resumes events. If retained history has expired, show the resulting history gap. Two phones each maintain their own cursor. The gateway does not delete an incident when one phone downloads it.
An event contains event_seq, database_epoch, event_type, created_at_ms and the affected entity ID and revision. Report events include report_id and report_revision; the app fetches that immutable report before committing its cursor. Return fewer than the requested event count when the byte limit is reached. Never skip sequence numbers merely to fit a page. For a paginated snapshot, retain a stable snapshot token and high-water sequence across every page. Commit the replacement cache and cursor only when all snapshot pages have arrived.
Store explanations by gateway_id, report_id, revision, Llama_model_id and prompt_version. A new action result produces a new report revision and requires a refreshed explanation. Keep previously generated text associated with its historical revision so it cannot misdescribe current execution status.
8.4 Local Llama explanation and chat
Start with a quantised Llama 3.2 1B Instruct model that can be exported through the selected ExecuTorch Android workflow. Provision the model, tokenizer and configuration in app-private storage, verify checksums, and record licence/access requirements. The exact export quantisation format must match the Android runner. A generic model file from another runtime is not automatically loadable as an ExecuTorch .pte bundle. [S7]
For 4 GB phones, start with a 1024-token total context and at most 128 generated tokens. For 8 GB phones, start with 2048 total tokens and at most 256 output tokens. These are test configurations rather than guaranteed compatibility. Context includes instructions, report, recent turns and output space. Store full reports separately and give Llama a compact fact selection that preserves execution status and critical measurements.
Implement one generation worker with cancellation and a bounded queue. Measure loading, time to first token and complete generation. Generate a short explanation once per incident revision while the app is active. Coalesce superseded pending revisions, cache outputs, and allow historical reports to be explained on demand. A burst of traffic should not create one Llama request per feature window. Keep the original factual summary immediately readable for every report.
The prompt supplies the selected report, a small reviewed glossary and approved troubleshooting suggestions. Require the model to distinguish observations, possible interpretations and suggested next steps. It must state the recorded execution status and acknowledge missing information. Questions about a report receive that report's structured facts and bounded recent dialogue. Questions about device history trigger a deterministic database query by the app, followed by a summary of the selected records. If the latest state matters, synchronise before answering or state the cached timestamp. The LLM cannot execute administrator commands. Restriction and release remain explicit UI actions with confirmation of target and scope.
Show the factual source fields beside the generated explanation. The text explains recorded evidence and policy logic; it does not reveal the CNN's internal causal reasoning. Validate a fixed set of explanations and questions manually, including benign false alerts, failed actions, missing data and malicious-looking device names.

11.3 Proposed acceptance rules
Schema mismatch, unknown action scope and unauthenticated access must be rejected. A repeated command must not create duplicate rules. A report must never mark an unconfirmed action as installed. The same feature fixture must pass the documented reference tolerance after export. A lost packet stream or failed CNN must appear as degraded monitoring.
For performance, define the VM profile and intended lab load before testing, initially up to 20 virtual clients with one prediction per second and a declared packet rate. Reduce and report the load if the host cannot sustain it. Use Python to record latency, CPU, RSS, queue depth and capture loss. Queues must remain bounded and losses visible. Passing proves the declared VM workload only; no physical-board or Arm64 check is required.
12 Operational limits and release decisions
Encrypted payloads, unobserved same-subnet traffic, ambiguous identities and attacks with benign-looking metadata limit coverage. Successful training on general network traffic does not establish accuracy for all consumer IoT devices. A binary score does not establish malware installation, attacker identity or recovery. Reports must preserve those distinctions.
The main avoidable implementation risks are inconsistent feature definitions, leakage between overlapping samples, device/victim confusion, stale results, conflicting firewall rules, silent data loss and incorrect action reporting. The contracts and acceptance checks above address these directly. Shared passwords provide a simple initial access model; separate user accounts and roles can extend it later.
Recommended implementation priority is contracts and a working pipeline first, then reproducible model experiments, then enforcement in the isolated lab, and finally broader deployment support. Preserve the complete enforcement interface from the beginning so the modules can be developed independently. A release can demonstrate OBSERVE mode while accurately describing ENFORCE as implemented, partially implemented or future work according to the actual test evidence.
PS3 currently lists local Llama advisory inference through ExecuTorch as required and provides IDS datasets as optional technologies. Its application areas include IoT monitoring, while its description also names phishing and scams. Record any organiser clarification of the network-focused scope. Phase 1 requires code, application, demo and a technical report. [S16]
